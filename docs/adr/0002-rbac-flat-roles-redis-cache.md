# RBAC：扁平角色 + Redis 缓存 + 权限驱动路由

选用 RBAC（基于角色的访问控制），权限码格式 `resource:action`，角色独立无继承，用户多角色并集生效。后端权限列表缓存在 Redis 中，登录不嵌入 JWT。前端路由由权限配置动态注册。

## 决策

- **扁平角色**（而非层级继承）：每个角色独立持有权限列表，用户多角色取并集。避免隐式继承的"排除规则"复杂度。
- **Redis 缓存**（而非 JWT 内嵌）：权限列表缓存在 Redis（key `permissions:<userId>`），长驻，修改角色时主动清缓存。好处是改权限即时生效，不依赖 token 过期。
- **分散式路由配置**（而非集中声明）：每个 feature 自描述其路由和权限要求（`route-config.ts`），authenticated 层按当前用户权限过滤后动态注册。侧边栏由同一份配置渲染。
- **`<Can>` 组件**（而非 hook 内联）：前端按钮级权限用声明式组件包裹。
- **通配 `*:*`**：预置 `admin` 角色持有全部权限。

## 考虑的替代方案

| 选项 | 否决原因 |
|------|---------|
| 层级角色（admin ⊇ manager ⊇ member） | 引入排除规则时复杂度爆炸；90% 场景用多角色并集足够 |
| JWT 嵌入权限 | 改权限需等 token 过期；权限多时 JWT 体积膨胀 |
| Casbin / Oso 等外部策略引擎 | 模板项目不引入额外依赖；RBAC 足够覆盖需求 |
| 集中路由配置 | 与项目 feature 目录结构冲突；加新 feature 需改集中文件 |

## 后续影响

- 多租户/作用域角色暂不引入（`user_roles` 无 scope 字段）。需要时加列 + 改缓存 key + 中间件感知 scope，各层都要改，但不难。
- ABAC 层（"本人资源"模式）不内置，由具体项目按需加。
